# TextInspector Pro 1.1.0 dataset fit review for Unclaimable 1.0.0

Source: `Perry3Dnl/TextInspectorPro`, branch `release/1.1.0`, `Presets/rules.json`.
Owner has authorized reuse of data. Check third-party provenance separately where applicable.
Stage: `data/imports/textinspector-pro-1.1.0.review.json`, not included as an embedded runtime dataset.

## Initial screening (2026-10-22)

- Extracted **4,782 source entries** in **23 groups**, from literal regex alternatives only; no engine code or regex execution is imported.
- **4,626 distinct NFKC + case-insensitive source values** across all groups, leaving 156 extra occurrences within/across groups. **144 normalized terms occur in multiple source groups.**
- **46 source entries have at most three UTF-16 code units; 503 have four to five.** These are structural risk indicators for indiscriminate substring matching, not proof the entries are invalid.
- **1,237 source entries contain non-ASCII characters.** Confirm Unicode normalization and language-specific casing behavior before enabling.
- The preliminary check against only `Extended/Data/slangprofanity.json` and `Extended/Data/hatespeech.json` already found 313 overlaps, including **all 112 expanded hate-speech phrases and all 110 regional slang entries**. These figures must not be mistaken for complete Core+Extended overlap counts.
- A comprehensive Core+Extended overlap report is generated by `python3 tools/audit_textinspector_import.py --json artifacts/textinspector-import-audit.json`, now added to CI. Do not publish a unique-addition count until this report is reviewed.

## Proposed decision by group

| Source data | Fit | Migration policy |
| --- | --- | --- |
| 15 localized profanity lists (4,035 source entries) | Candidate with substantial false-positive risk | Compare to existing language entries. Distinguish insult words from unequivocal profanity. Hold short/multilingual collisions for manual review, and never make novel matches default-on in 1.0.0 without an approved behavior-change exception. |
| Regional slang (110) | Already present in checked Extended list | Skip duplicates; no import benefit until a more exact Core comparison proves otherwise. |
| Hate-speech supplement (112) | Already present in checked Extended list | Skip duplicates; preserve existing curated matching modes. |
| Multilingual official roles (82) | Useful for impersonation but context-dependent | Opt-in identity dataset, exact/whole identifier behavior preferred; common roles alone are not necessarily impersonation. |
| Government organizations (175) | Strong identity-protection use case | Opt-in identity categories; preserve multiword phrases; check generic identity collisions. |
| Crypto exchanges / protocols / wallets / projects (268) | Useful for opt-in protected names | Prefer exact/whole identifiers. Avoid generic project terms such as `Safe`, `Flow`, `Gala`, or `Rain` becoming global blacklist entries. |

## Reviewed representative cases

- Dutch `kut`, `lul`, `kak` and multilingual `nul`, `fan`: possibly valid in their native language, but high-risk as substrings embedded in ordinary unrelated names.
- `Safe`, `Flow`, `Gala`, `Rain`: ordinary-word collisions and poor candidates for default blocking.
- `Coinbase Wallet`: specific protected brand/service, suitable for opt-in identity protection after comparing normalized duplicates.
- `Home Office`, `Met Office`: named organizations in a particular jurisdiction; require category/region-specific semantics.
- Source-level exact lexical evidence does not imply Unclaimable should use partial, compact, or obfuscation matching on the same term.

## Compatibility decision

**No staged entry is activated yet.** Existing v0.8.5 users, including those who enabled `UseExtendedData()`, must not silently get new username rejections when upgrading to 1.0.0. Merely adding a new category to Extended is insufficient if `UseExtendedData()` enables new categories by default.

Activation requires: (1) full normalized duplicate audit, (2) human-reviewed category and scope, (3) explicit opt-in semantics where new behavior is introduced, (4) acceptance/rejection differential corpus against v0.8.5, and (5) passing six-package CI plus package/API backward-compatibility checks.

This report is an initial engineering fit review, **not** a claim that all 4,782 values have received individual linguistic validation.
